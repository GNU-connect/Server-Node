# 도메인별 요구사항

## 기준

- 원본 시나리오: [유저 시나리오.md](./유저%20시나리오.md)
- 목적: 사용자 시나리오를 바탕으로 도메인 모델을 도출하기 위한 요구사항을 도메인별로 정리한다.
- 범위: 카카오톡 챗봇과 모바일 앱에서 제공하는 학교 생활 정보 조회 기능

## 1. 사용자 설정 도메인

### 도메인 책임

사용자 설정 도메인은 사용자의 식별 정보와 개인화 기준이 되는 캠퍼스, 학과 정보를 관리한다. 다른 도메인은 사용자의 캠퍼스 또는 학과 설정을 조회 조건으로 사용할 수 있다.

### 주요 개념 후보

| 개념 | 설명 |
| --- | --- |
| 사용자 | 커넥트 지누를 통해 교내 정보를 조회하는 주체 |
| 사용자 프로필 | 사용자에게 저장된 캠퍼스와 학과 정보 |
| 캠퍼스 | 식당, 학과, 셔틀 등 학교 생활 정보의 기준이 되는 캠퍼스 |
| 단과대학 | 학과를 그룹화하는 상위 조직 |
| 학과 | 사용자 개인화와 학과 공지사항 조회의 기준이 되는 조직 |

### 기능 요구사항

- 시스템은 사용자가 챗봇을 사용할 때 사용자를 식별할 수 있어야 한다.
- 시스템은 사용자별로 캠퍼스와 학과 정보를 저장할 수 있어야 한다.
- 시스템은 사용자의 저장된 캠퍼스와 학과 정보를 조회할 수 있어야 한다.
- 저장된 캠퍼스와 학과가 없는 사용자는 미설정 상태로 처리해야 한다.
- 사용자는 캠퍼스, 단과대학, 학과 순서로 자신의 학과 정보를 등록하거나 변경할 수 있어야 한다.
- 사용자가 캠퍼스를 선택하면 시스템은 해당 캠퍼스의 단과대학 목록을 제공해야 한다.
- 사용자가 단과대학을 선택하면 시스템은 해당 단과대학의 학과 목록을 제공해야 한다.
- 학과 저장이 완료되면 시스템은 선택한 캠퍼스와 학과를 사용자 프로필에 반영해야 한다.

### 정책 및 제약

- 단과대학 목록은 한 화면에 최대 5개씩 제공한다.
- 학과 목록은 한 화면에 최대 5개씩 제공한다.
- 목록이 5개를 초과하면 이전/다음 탐색을 통해 나머지 항목을 확인할 수 있어야 한다.
- 학과 공지사항 조회는 사용자 학과 정보가 등록되어 있어야 사용할 수 있다.
- 학식 조회는 사용자가 직접 캠퍼스를 선택하지 않은 경우 저장된 캠퍼스를 기본 조회 조건으로 사용할 수 있다.

### 예외 요구사항

- 사용자 처리 중 예상하지 못한 문제가 발생하면 오류 메시지를 제공해야 한다.
- 선택한 캠퍼스, 단과대학, 학과 정보를 찾을 수 없으면 오류 상태로 처리해야 한다.
- 저장된 프로필 정보가 없으면 캠퍼스와 학과를 미설정 상태로 표시해야 한다.

## 2. 공지사항 도메인

### 도메인 책임

공지사항 도메인은 학교 전체 공지사항과 사용자의 학과 공지사항을 최신순으로 제공한다. 사용자는 공지 목록에서 원문으로 이동할 수 있어야 한다.

### 주요 개념 후보

| 개념 | 설명 |
| --- | --- |
| 공지사항 | 학교 또는 학과에서 게시한 안내 글 |
| 학교 공지사항 | 학교 전체 기준으로 제공되는 공지사항 |
| 학과 공지사항 | 특정 학과 또는 관련 상위 학과 기준으로 제공되는 공지사항 |
| 공지 카테고리 | 학교 공지사항을 분류하는 기준 |
| 공지 분류 | 학과 공지사항을 묶어 보여주는 분류 |
| 원문 링크 | 사용자가 공지사항 상세 내용을 확인할 수 있는 외부 또는 내부 경로 |

### 기능 요구사항

- 시스템은 학교 전체 공지사항을 주요 카테고리별로 조회할 수 있어야 한다.
- 시스템은 학교 공지사항을 최신순으로 제공해야 한다.
- 시스템은 사용자의 학과 정보를 기준으로 학과 공지사항을 조회할 수 있어야 한다.
- 학과 공지사항 조회 시 필요한 경우 관련 상위 학과의 공지사항도 함께 조회해야 한다.
- 공지사항 목록에는 사용자가 원문을 확인할 수 있는 링크 또는 식별자가 포함되어야 한다.
- 챗봇과 모바일 앱은 공지사항을 사용자가 탐색하기 쉬운 카드 또는 목록 형태로 제공해야 한다.

### 정책 및 제약

- 학교 공지사항은 `기관`, `채용`, `장학`, `외부기관 행사`, `학사` 카테고리를 제공한다.
- 학교 공지사항은 각 카테고리마다 최신 공지사항을 최대 4개씩 제공한다.
- 학교 공지사항은 전체 최대 20개까지 제공한다.
- 학과 공지사항은 공지 분류별 최신 글을 최대 4개씩 제공한다.
- 관련 상위 학과 공지사항을 함께 제공하더라도 분류별 최대 4개 기준을 유지한다.
- 학과 공지사항은 사용자 프로필에 학과가 등록되어 있을 때 조회할 수 있다.

### 예외 요구사항

- 학교 공지사항이 없으면 현재 등록된 공지사항이 없음을 안내해야 한다.
- 학과 공지사항 조회 시 사용자 학과 정보가 없으면 학과 등록을 먼저 안내해야 한다.
- 학과 공지사항이 없으면 현재 등록된 공지사항이 없음을 안내해야 한다.

## 3. 학식 도메인

### 도메인 책임

학식 도메인은 캠퍼스별 식당 목록과 식당별 식단을 제공한다. 사용자는 캠퍼스, 식당, 날짜, 끼니를 기준으로 메뉴를 조회할 수 있다.

### 주요 개념 후보

| 개념 | 설명 |
| --- | --- |
| 캠퍼스 | 식당 목록을 구분하는 기준 |
| 식당 | 특정 캠퍼스에 속한 학식 제공 장소 |
| 식단 | 특정 식당, 날짜, 끼니에 제공되는 메뉴 정보 |
| 끼니 | 아침, 점심, 저녁 중 하나의 식사 구분 |
| 메뉴 분류 | 식단 메뉴를 묶어 보여주는 분류 |
| 조회 조건 | 캠퍼스, 식당, 날짜, 끼니 조합 |

### 기능 요구사항

- 시스템은 캠퍼스 목록을 제공할 수 있어야 한다.
- 시스템은 캠퍼스별 식당 목록을 제공할 수 있어야 한다.
- 사용자가 챗봇에서 학식을 조회하면 시스템은 선택한 캠퍼스 또는 저장된 캠퍼스를 기준으로 식당 목록을 제공해야 한다.
- 사용자는 식당을 선택한 뒤 날짜와 끼니를 선택해 메뉴를 조회할 수 있어야 한다.
- 시스템은 특정 식당의 특정 날짜, 특정 끼니에 해당하는 식단을 조회할 수 있어야 한다.
- 끼니가 직접 선택되지 않으면 시스템은 현재 시간을 기준으로 끼니를 자동 선택해야 한다.
- 날짜가 직접 선택되지 않으면 시스템은 현재 시간을 기준으로 오늘 또는 내일을 자동 선택해야 한다.
- 모바일 앱은 캠퍼스, 식당, 날짜, 끼니 선택 상태에 맞는 메뉴를 조회할 수 있어야 한다.
- 메뉴는 분류별로 묶어 제공해야 한다.

### 정책 및 제약

- 챗봇에서는 `오늘 아침`, `오늘 점심`, `오늘 저녁`, `내일 아침`, `내일 점심`, `내일 저녁` 6개 빠른 선택지를 제공한다.
- 모바일 앱에서는 오늘부터 7일간의 날짜를 선택할 수 있다.
- 끼니는 아침, 점심, 저녁 중 하나이다.
- 끼니 자동 선택 기준은 다음과 같다.
  - 19:00부터 다음 날 09:29까지는 아침으로 본다.
  - 09:30부터 13:29까지는 점심으로 본다.
  - 13:30부터 18:59까지는 저녁으로 본다.
- 챗봇에서 날짜를 직접 선택하지 않은 경우 19:00 전에는 오늘, 19:00 이후에는 내일 메뉴를 보여준다.
- 챗봇의 자동 선택 기준은 한국 시간 기준으로 판단한다.
- 모바일 앱의 자동 선택 기준은 휴대폰에 설정된 현재 시간 기준으로 판단한다.

### 예외 요구사항

- 선택한 캠퍼스도 저장된 캠퍼스도 없으면 캠퍼스 선택을 안내해야 한다.
- 해당 캠퍼스에 등록된 식당이 없으면 식당 정보가 없음을 안내해야 한다.
- 선택한 식당 정보를 찾을 수 없으면 오류 상태로 처리해야 한다.
- 선택한 날짜와 끼니에 등록된 메뉴가 없으면 메뉴가 없음을 안내해야 한다.
- 모바일 앱에서 캠퍼스, 식당, 메뉴 정보를 불러오지 못하면 각각의 실패 메시지를 제공해야 한다.

## 4. 학사일정 도메인

### 도메인 책임

학사일정 도메인은 사용자가 선택한 월 또는 현재 월의 학사일정을 제공한다.

### 주요 개념 후보

| 개념 | 설명 |
| --- | --- |
| 학사일정 | 학교의 학사 관련 일정 |
| 조회 월 | 학사일정을 조회하는 월 단위 조건 |
| 일정 항목 | 특정 기간 또는 날짜에 해당하는 학사 이벤트 |

### 기능 요구사항

- 시스템은 특정 월의 학사일정을 조회할 수 있어야 한다.
- 사용자가 월을 선택하면 시스템은 해당 월의 학사일정을 제공해야 한다.
- 사용자가 월을 선택하지 않으면 시스템은 현재 월의 학사일정을 제공해야 한다.
- 챗봇은 조회된 학사일정을 사용자가 읽을 수 있는 형태로 제공해야 한다.

### 정책 및 제약

- 조회 월은 1부터 12 사이의 값이어야 한다.
- 월 선택이 없는 경우 현재 월을 기본 조회 조건으로 사용한다.

### 예외 요구사항

- 올바르지 않은 월을 선택하면 올바른 월 입력을 안내해야 한다.
- 해당 월에 등록된 학사일정이 없으면 일정이 없음을 안내해야 한다.

## 5. 셔틀버스 도메인

### 도메인 책임

셔틀버스 도메인은 제공 중인 셔틀 노선과 노선별 시간표를 관리한다. 모바일 앱에서는 현재 시간 기준 다음 버스를 계산해 강조해서 제공한다.

### 주요 개념 후보

| 개념 | 설명 |
| --- | --- |
| 셔틀 노선 | 출발 캠퍼스와 도착 캠퍼스를 가지는 운행 경로 |
| 셔틀 시간표 | 특정 노선의 운행 시간 목록 |
| 운행 구간 | 시간표를 묶어 보여주는 구간 |
| 운행 시간 | 셔틀이 특정 구간에서 출발하거나 도착하는 시간 |
| 다음 버스 | 현재 시간 이후 가장 가까운 운행 |
| 운행 예외 | 금요일 미운행 등 특정 조건에서 운행하지 않는 시간 |

### 기능 요구사항

- 시스템은 등록된 셔틀 노선 목록을 제공할 수 있어야 한다.
- 사용자는 셔틀 노선 목록에서 원하는 노선을 선택할 수 있어야 한다.
- 시스템은 선택한 노선의 시간표를 제공할 수 있어야 한다.
- 챗봇은 선택한 노선의 시간표를 구간별로 묶어 제공해야 한다.
- 모바일 앱은 셔틀 노선 목록을 제공하고 첫 번째 노선을 기본으로 선택해야 한다.
- 모바일 앱은 사용자가 노선을 변경하면 해당 노선의 시간표를 다시 보여줘야 한다.
- 모바일 앱은 현재 시간 기준으로 가장 가까운 다음 버스를 계산해야 한다.
- 모바일 앱은 이미 지난 시간, 다음 버스 시간, 앞으로 남은 시간을 구분해 보여줘야 한다.
- 모바일 앱은 사용자가 갱신 버튼을 누르면 시간표를 즉시 새로 불러올 수 있어야 한다.
- 모바일 앱은 일정 시간마다 시간표를 새로 확인해 최신 상태를 유지해야 한다.

### 정책 및 제약

- 현재 제공 노선은 `가좌 → 칠암 캠퍼스`, `칠암 → 가좌 캠퍼스` 2개이다.
- 시간표는 구간별로 묶어 보여준다.
- 금요일에 운행하지 않는 시간은 별도 표시로 구분한다.
- 다음 버스는 현재 시간 이후 가장 가까운 1개만 강조한다.
- 모바일 앱은 시간표를 1분마다 자동으로 새로 확인한다.

### 예외 요구사항

- 등록된 노선이 없으면 노선 정보가 없음을 안내해야 한다.
- 선택한 노선 정보를 찾을 수 없으면 오류 상태로 처리해야 한다.
- 모바일 앱에서 노선 정보를 불러오지 못하면 노선 정보 조회 실패 메시지를 제공해야 한다.
- 모바일 앱에서 시간표를 불러오지 못하면 시간표 조회 실패 메시지를 제공해야 한다.
- 오늘 남은 운행이 없으면 운행이 종료되었음을 안내해야 한다.

## 7. 공통 요구사항 후보

- 모든 조회 기능은 데이터가 없는 상태와 시스템 오류 상태를 구분해야 한다.
- 챗봇과 모바일 앱은 같은 도메인 규칙을 공유하되, 표시 방식과 기본 선택 정책은 채널 특성에 맞게 다를 수 있다.
- 시간 기반 자동 선택은 기준 시간대와 경계 시간을 명확히 정의해야 한다.
- 외부 원천 데이터의 부재, 변경, 삭제에 대비해 찾을 수 없는 정보에 대한 예외 처리가 필요하다.
- 도메인 모델은 조회 조건, 표시 정책, 예외 메시지를 분리해 변경 가능성을 낮춰야 한다.
